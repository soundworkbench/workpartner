# 在 Kubernetes 上运行每人工作区和网关

## 合同

### 结果

做完以后：

- 网关可以在 Kubernetes 集群里管理每个人的工作区。组织配置写 `runtime.kind: "k8s"` 即可切换。
- 网关本身作为 Pod 运行，固定在控制面节点。
- 每人工作区是副本数为 1 的 StatefulSet，可以分布在多台节点上。
- 已有用户的数据留在原节点、原目录。新用户按组织配置的节点规则落到另一台节点。

感受得到的变化：

- 用户：网页、飞书机器人、预览、技能市场、飞书授权的用法和现在一样。迁移期间机器人不掉线，同一个人在任何时刻只有一份机器人连着飞书。
- 管理员：
  - 镜像按节点导入，不需要镜像仓库。
  - 出站隔离从宿主 iptables 改为 NetworkPolicy，节点上另有 nft 兜底，并能用探针复验。
  - 容器层的个人补丁改放在 `/data/.zp-init.d/`，重建后不会丢。
- 网关以 Docker 模式运行时（缺省）：行为与改动前完全一致。

### 范围

做：

1. `gateway/runtime/` 下新增 Kubernetes API 客户端（不加依赖）和 k8s 运行时。`runtime/index.mjs` 按 `runtime.kind` 选择实现。
2. 网关在 k8s 模式下的行为：
   - 不加载组织扩展；
   - 按归属文件把不归自己管的用户转发给另一套网关；
   - 飞书授权维护只处理自己名下的用户；
   - 对自己名下、已存在但副本为 0 的用户做常驻保障。
3. 两种网关都支持的「迁移归属」：同一时刻每个人只归一套网关管，另一套不对这个人做生命周期操作。
4. 镜像 `start.sh`：
   - 通用启动钩子 `/data/.zp-init.d/`；
   - 网关发布文件（令牌、CLI 配置、预览密钥）在 `/data` 下的链接；
   - `wait -n` 只等自己启动的进程。
5. 部署清单模板和渲染工具，内容包括：
   - 命名空间、PSA 标签、RBAC；
   - 网关 Deployment，以及与网关同名的 headless Service；
   - 模型出口的同名 Service；
   - NetworkPolicy、新用户 StorageClass、镜像登记 ConfigMap。
6. 节点 nft 兜底的脚本和 systemd 单元模板；按节点 `ctr import` 的镜像分发工具。
7. 存量用户接管工具：
   - 建静态 local PV/PVC；
   - 切换、回滚、预热、核对；
   - 盘点容器层补丁。
8. 端到端测试：k3d 启停脚本、测试镜像、场景脚本、清理。
9. 文档：`docs/organization.md`、`docs/deployment.md`、新增 `docs/kubernetes.md`；类型声明 `gateway/organization/resolve.d.mts`。

不做：

- 不建镜像仓库，不引入 Helm/Kustomize/CRD/Operator。
- 不迁移旧版后端（backend 不是 aionui 的用户）的容器。旧版用户继续由 Docker 网关服务（见已定的决定 11）。
- 不搬已有用户的数据，不做跨节点数据复制或备份方案（另立任务）。
- 不改模型出口程序本身。模型出口工作负载的镜像、参数、凭据由组织私有部署提供，本仓库只渲染它的 Service 和网络规则。
- 不改 k3s 启动参数，不改宿主现有防火墙规则；nft 兜底是新增的独立表。
- 不删除任何 Docker 容器、网络和数据目录（只停，不删）。

### 约束

**仓库与代码**

- 开源仓库：代码、注释、测试、文档、提交信息里不写公司名、人名、IP、域名、节点主机名。
  - 组织参数只能来自组织配置。配置项见下面的「配置项」。
  - 节点公网地址、宿主路径、节点标签值都属于私有配置。
- 不加依赖。Kubernetes 访问只用 Node 24 自带的 `https`、`http` 和已有的 `ws`。
  - kubeconfig 只接受 JSON（`kubectl config view --raw --minify --flatten -o json` 的输出）。
  - 集群内使用 ServiceAccount：令牌文件每次请求前重新读取，因为绑定令牌会轮换。
- 注释和标识符用英文，与现有风格一致，只写必要的注释。测试测行为：像调用方那样调用，断言具体值。
- Codex 沙箱无网络、无集群：单元测试必须离线可跑。端到端测试由协调者在沙箱外跑。

**Docker 模式不能变**

- 不写 `runtime.kind`，或写 `"docker"` 时，Docker 运行时行为与 main（ce6a3a5）一致。
- 没有 `runtime.migration` 时，两种网关都按「所有人都归自己」处理。

**只用的 API 和对象**

- 只用 core/v1、apps/v1、networking.k8s.io/v1，不依赖 watch，用轮询加超时。
- 所有写操作都要能重复执行，结果一致：已存在就核对，必要时更新；404 视为已删除。

**单实例**（任何改动都不能破坏）

1. 每人只有一个 StatefulSet，`replicas` 只取 0 或 1，`updateStrategy: OnDelete`。
2. `stop` 和 `remove` 都要等到该用户的 Pod 对象真正消失才返回。
3. `runOnce` 只在该用户没有任何 Pod 时执行，返回前等一次性 Pod 删除完毕。
4. 迁移时，Docker 容器先停、并设 `restart=no`，再写归属文件，最后才启动 Pod。回滚按相反顺序。

**安全**

- 用户命名空间：
  - PSA `enforce=baseline`、`warn=restricted`；
  - 不挂宿主目录（hostPath），不建 NodePort/LoadBalancer；
  - 用户 Pod 不挂 ServiceAccount 令牌（`automountServiceAccountToken: false`）、`enableServiceLinks: false`。
- 主容器：
  - 以 `runtime.uid` 运行，`runAsNonRoot`；
  - `allowPrivilegeEscalation: false`、`capabilities.drop: [ALL]`、`seccompProfile: RuntimeDefault`。
- 只有初始化容器以 root 运行，只加 `CHOWN` 能力，只执行 `chown <uid>:<uid> /data`，不递归。
- 网关 RBAC 只给需要的权限：
  - 用户命名空间：statefulsets、pods、pods/exec、pods/log、secrets、persistentvolumeclaims、networkpolicies（只读）；
  - 系统命名空间：pods/exec（execNamed 用）、configmaps（只读）；
  - 不给集群级权限。静态 PV 由管理员工具用管理员凭据创建。
- 钥匙、令牌、Secret 的内容不进日志、错误信息和测试快照。

**资源**

- 每人 Pod：
  - requests：内存 `runtime.k8s.memoryRequest`（缺省 512Mi）、CPU `runtime.k8s.cpuRequest`（缺省 100m）；
  - limits：内存取 `runtime.nextMemory`，CPU 取 `runtime.nanoCpus / 1e9`；
  - 进程数上限靠节点 kubelet 的 `pod-max-pids`，两台节点都要核实。
- 网关 Pod 设成 Guaranteed（requests = limits），并使用部署清单里的高优先级 PriorityClass。

**镜像**

- `imagePullPolicy: Never`。
- 镜像必须先由分发工具导入所有目标节点，并登记到镜像 ConfigMap，`create` 才会使用。未登记的镜像直接报错，不建出一直 Pending 的 Pod。
- 分发工具给导入的镜像加 `io.cri-containerd.pinned=pinned` 标签，防止 kubelet 镜像回收把它删掉。

**名称与标签**（固定规则，写进文档）

- 用户名称：
  - 用户代号必须匹配 `^[a-z][a-z0-9-]{1,30}$`，否则 k8s 运行时直接拒绝。
  - 记 `<c>` = `runtime.nextContainerPrefix + slug`。StatefulSet 名为 `<c>`，Pod 名为 `<c>-0`。
- 用户相关对象：
  - 数据卷 PVC：`<c>-data`。旧工作目录只读卷：`<c>-oldwork`，可选，存在才挂。
  - 钥匙 Secret：`<c>-model-key`。发布文件 Secret：`<c>-published`。
  - 一次性 Pod：`<c>-<name>`。
- 标签：
  - `app.kubernetes.io/part-of: workpartner`；
  - `workpartner/role`：取 user、job、gateway、model-egress 之一；
  - `runtime.nextUserLabel: <slug>`，启动时校验它是合法的标签键。
- 注解：`workpartner/image-id`、`workpartner/paused`。

**已接受的差异**（只允许这些，其余都要与 Docker 一致）

1. `exec`：
   - 不能指定其他用户。`user` 不是容器用户（`uid` 或 `uid:uid`）时报错。
   - `env` 改成在命令前加 `env K=V ...`。
   - `createTimeout` 作为建连和握手的超时。
2. `detached` exec 用 `setsid` 包装后立即返回 `exitCode: null`。孤儿进程由容器 1 号进程收养；配套地，`start.sh` 只等自己启动的进程（K4）。
3. `processes` 在容器内读取 `/proc` 得到结果。pid 和 ppid 是容器内的编号，按字符串返回，与 Docker `/top` 一样只用于比较父子关系。
4. 文件属主：
   - 经 exec 写入的文件一律属于容器用户，`owner: false` / `chown: false` 不再生效；
   - 发布文件和钥匙放在 Secret 卷里，属主 root、权限 0444。容器内只有本人一个用户。
5. `/data` 根目录的创建和属主由 PVC 加初始化容器负责，`putFiles` 的 `directoryMode` 对根目录不生效。
6. 主机名是 Pod 名 `<c>-0`，不再是容器名。镜像脚本没有用到主机名，端到端测试会再核实。
7. `restart` 是删 Pod 后等新 Pod 运行，地址会变。调用方每次请求都会重新 inspect，不受影响。
8. `imageId` 来自镜像 ConfigMap 的登记值。inspect 的 `imageId` 取 StatefulSet 上 `workpartner/image-id` 注解，即创建时的登记值。
9. inspect 和镜像查询各有短缓存：inspect ≤ `runtime.k8s.inspectCacheMs`（缺省 2000 ms），镜像 ≤ 10 s。本运行时自己的生命周期操作会立即清掉缓存。

**配置项**（私有组织配置里给值；本仓库只给缺省值和说明）

- 网关读取：
  - `runtime.kind`：`"docker"`（缺省）或 `"k8s"`。
  - `runtime.k8s.namespace`：用户工作负载所在命名空间，必填。
  - `runtime.k8s.systemNamespace`：网关和模型出口所在命名空间，缺省取 ServiceAccount 的命名空间。
  - `runtime.k8s.clusterDomain`：缺省 `cluster.local`。
  - `runtime.k8s.apiTimeoutMs`：缺省 10000。
  - `runtime.k8s.storageClass`：新用户数据卷的存储类，必填。`runtime.k8s.dataVolumeSize`：缺省 `20Gi`，local-path 不强制。
  - `runtime.k8s.newUserNodeSelector`：新用户 Pod 的节点选择，缺省 `{}`。只在数据卷尚未绑定时写进 Pod 模板。
  - `runtime.k8s.memoryRequest`、`runtime.k8s.cpuRequest`：见「资源」。
  - `runtime.k8s.userPriorityClass`：可选。
  - `runtime.k8s.imageConfigMap`：缺省 `workpartner-images`，在系统命名空间。数据键 `images.json` 的内容是 `{ref: imageId}`。
  - `runtime.k8s.governingService`：缺省 `workpartner-users`。
  - `runtime.k8s.requiredPolicies`：缺省 `["workpartner-default-deny","workpartner-user-egress","workpartner-user-ingress"]`。
  - `runtime.k8s.publishedDirectory`：缺省 `/run/workpartner/published`。
  - `runtime.k8s.publishedFiles`：缺省 `[".zp-market-token",".wp-feishu-cli.json",".zp-preview-relay-key"]`。
  - `runtime.k8s.podStartTimeoutMs`：缺省 120000。`runtime.k8s.terminationGraceSeconds`：缺省 10。
  - `runtime.k8s.inspectCacheMs`：见「已接受的差异」第 9 条。
  - `runtime.k8s.keepRunningIntervalMs`：缺省 300000，0 表示关闭。
  - `runtime.k8s.loadGatewayExtension`：缺省 false。
  - `runtime.migration.ownersFile`：归属文件路径。网关只读，迁移工具写。
  - `runtime.migration.peerOrigin`：另一套网关的内部地址；不填就不转发。
- 只有渲染工具读取（`runtime.k8s.deploy.*`）：
  - `gatewayImage`、`gatewayNodeSelector`（缺省 `node-role.kubernetes.io/control-plane: "true"`）；
  - `entry`：`{mode: "hostPort", hostIP, hostPort}`，或回退用的 `{mode: "clusterIP", clusterIP}`；
  - `hostPaths`：organization、secure、state、usersFile；
  - `egressExceptCidrs`：所有节点的公网地址 /32 等；
  - `modelEgressSelector`、`newUserStorage`：provisioner 参数。

### 停止条件

遇到下面任何一种情况，停下来问用户：

1. 首次在正式节点上加载 nft 兜底、改任何正式节点的防火墙或 k3s 参数（含 kubelet 预留和驱逐阈值）之前。
2. 需要新凭证：测试身份应用、测试模型钥匙、模型出口凭据进集群 Secret。
3. R3「切正式入口」之前，以及 R4 第一批开始之前，等用户明确说「切」。之后各批按用户同意的节奏走。
4. 任何删除操作：删 Docker 容器、网络、数据目录、PV 目录，或删除旧网关。
5. 发现同一个人同时有两份实例在跑（Docker 容器和 Pod 并存，或两个 Pod），或者疑似重复连接飞书。先停新的那份，再报告。
6. 网络探针有任何一项不符合预期，或者 nft 兜底和现有宿主规则冲突。
7. 要改已定的决定。例如：
   - `hostPort` 绑本机回环不可用，要改成 ClusterIP 入口（这会改隧道的目标地址）；
   - 要改成建镜像仓库；
   - 要搬数据。
8. 容器层补丁盘点发现无法以非 root 方式还原的补丁（例如必须改 `/usr/local/bin` 下的文件、而且不能用 PATH 覆盖），并且涉及身份分流（例如 CLI 选错租户）。
9. 集群证据与本规格的假设不一致。例如 local-path 不支持 StorageClass 参数、PSA 标签不生效、kube-router 不处理 INPUT 方向。

### 已定的决定

1. 采用路径 A：
   - 在现有运行时接口上新写 `gateway/runtime/k8s.mjs`，用 `runtime.kind=k8s` 切换，接口方法全部实现；
   - exec、top、logs、runOnce 改走 Kubernetes API，putFiles 和 readFile 不再假定宿主目录。

   用户，2026-11-10。
2. 网关本身作为 Pod 进集群，固定在控制面节点，配同名 Service。容器内按名字访问网关和模型出口的方式不变，对外入口仍由宿主上的隧道连本机端口。用户，2026-11-10。
3. 每人一个副本数为 1 的 StatefulSet，不允许两份同时连飞书。数据用静态 local PV 指向原数据目录，钥匙和令牌放 Secret。用户，2026-11-10。
4. 现有用户留在原节点、数据不搬。新用户默认调度到另一台节点，节点选择规则放组织配置。用户，2026-11-10。
5. 出站隔离：
   - 用 NetworkPolicy 替代现在的 iptables 出站限制；
   - 节点上另加 nft 兜底「禁止访问宿主」；
   - 两者都要有探针实测。

   用户，2026-11-10。
6. 镜像按节点 `ctr import` 分发，不建镜像仓库。用户，2026-11-10。
7. 镜像 `start.sh` 加通用启动钩子，启动时执行 `/data/.zp-init.d/` 下的脚本。用户，2026-11-10。
8. 每人 Pod 的 requests 512Mi、limits 3Gi，接受超卖。用户，2026-11-10。
9. 灰度顺序：先测试网关加测试用户，再切正式网关，先试点一人，之后每批约 10 人。用户，2026-11-10。
10. 实现细节，由协调者在本规格中确定，2026-11-11：
    - 发布文件放 Secret，挂在 `runtime.k8s.publishedDirectory`，由 `start.sh` 在 `/data` 下建同名链接。
    - 非发布文件经 exec 写入，执行容器内 Node 的固定脚本，参数从 stdin 传入，不拼 shell。
    - 新用户的数据卷由 StorageClass 动态创建，存量用户由接管工具建静态 PV。
    - 网关入口优先用 `hostPort` 绑本机回环地址，保持隧道配置不变。
11. 旧版扩展直接调 docker.sock 的问题，处理办法如下（协调者定，2026-11-10）：
    - k8s 网关不挂 docker.sock，也不加载组织扩展。
    - 旧版用户和尚未迁移的用户，都由 Docker 网关继续服务。k8s 网关按归属文件，把这些人的浏览器请求整段转发给 Docker 网关（`runtime.migration.peerOrigin`）。
    - Docker 网关保留 docker.sock 和旧版扩展。它的端口只发布在 Docker 网桥地址上，供 k8s 网关 Pod 访问，不对外。
    - 旧版用户清零之后，Docker 网关再下线，另行决定。
12. 灰度期间两套网关并存（协调者定，2026-11-10）：
    - 从 R3 起，k8s 网关作为唯一对外入口；
    - 归属文件决定每个人归哪套网关；
    - 飞书授权维护、令牌刷新、常驻保障只对自己名下的人做。

  - 子命令（默认都是 dry-run，加 `--apply` 才真正执行）：
    - `pv <slug> --node <节点名> --data-root <目录>`：建静态 local PV 和 PVC `<c>-data`，带节点亲和、`Retain`、`claimRef`；旧工作目录存在时一并建 `<c>-oldwork`，只读。
    - `inventory <slug>`：
      - 用 `docker diff` 列出容器层的改动；
      - `/usr/local/bin` 下新增或修改的可执行文件，复制到 `/data/.zp-init.d/bin/`，属主为用户；
      - 其余改动列进报告，不处理。
    - `switch <slug>`，按以下顺序执行：
      1. 前置检查：PVC 已绑定，镜像已登记；
      2. 把 Docker 容器设为 `restart=no` 并停止；
      3. 在归属文件里把这个人设为 k8s（原子写）；
      4. 用 k8s 运行时执行 ensureIsolation、create、start 预热；
      5. 执行 `verify`。
    - `rollback <slug>`，按以下顺序执行：
      1. 停掉 StatefulSet 并等 Pod 消失；
      2. 在归属文件里把这个人设为 docker；
      3. 删掉 `/data` 下指向发布目录的链接；
      4. 把 Docker 容器设为 `restart=unless-stopped` 并启动。
    - `verify <slug>`：
      - Pod 运行中，并且在预期节点上；
      - 网关侧能访问 AionUi 的状态接口；
      - cc-connect 进程存在（有配置的人）；
      - 预览密钥链接有效；
      - 没有正在运行的同名 Docker 容器。
    - `status`：列出所有人的归属、Pod 状态、Docker 容器状态。出现下面三种情况就报警，并以非零码退出：
      - 归 k8s 但 Docker 容器在跑；
      - 归 docker 但 Pod 存在；
      - 同一个人有一个以上 Pod。
  - 验收：
    - 用假 docker、假客户端、临时归属文件的测试覆盖：
      - 各子命令的步骤顺序（断言调用序列）；

      - dry-run 不发任何写操作；
      - `status` 的三类报警。

  - 场景：
    - S1 生命周期：
      - create 之后 inspect 显示存在但未运行；
      - 依次执行 start、stop、start、restart，restart 后 Pod uid 改变；
      - remove 后 StatefulSet 消失、PVC 保留；
      - 重新 create、start，之前写的文件还在。
    - S2 单实例：
      - 乱序并发 start、stop、restart、runOnce 各 10 次，同时每 200 ms 列一次 Pod；
      - 断言：同一个人任何时刻未终止的 Pod 不超过 1 个，一次性 Pod 不和主 Pod 同时存在。
    - S3 exec：
      - 退出码 0 和非 0，stdout 和 stderr 分开，logs 保持顺序；
      - stdin、输出超限、超时、env 包装都按预期；
      - 指定其他用户时报错；
      - detached 执行之后，被启动的进程还活着，主容器 restartCount 不变。
    - S4 processes：能找到假 cc-connect 的子进程。
    - S5 文件：
      - 发布文件写入后 90 秒内，容器里能经 `/data` 原路径读到；更新后也能读到新内容；
      - ENOENT、暂存租约、非法路径、符号链接不被跟随都按预期。
    - S6 runOnce：
      - 主 Pod 在跑时被拒绝；停掉后能执行，日志里有口令行，退出码正确；
      - 一次性 Pod 无法联网，在 Pod 内连网关会失败；
      - 结束后一次性 Pod 被删除。
    - S7 镜像：
      - 改 ConfigMap 里登记的 ID 后，按 ID 判断为过期；
      - 未登记的镜像 create 时报错。
    - S8 调度：
      - `newUserNodeSelector` 指向 agent 节点时，新用户 Pod 落在 agent 上；
      - 静态 PV 用例：有节点访问能力时才跑，Pod 落在 PV 所在节点；没有就记为 SKIP。
    - S9 失败即关闭：删掉一条必需的 NetworkPolicy 后 start 被拒绝；恢复后正常。
    - S10 网络矩阵：用户 Pod 在两台节点上各放一个。
      - 网关名的 DNS 结果等于网关 Pod 的 IP。
      - 应该通：网关的 gatewayPort 和 internalPort；模型出口端口；外网（只在给了 `--external-probe` 时测）；网关访问用户的 25808 和 3092。
      - 应该不通：
        - 网关的其他端口；
        - 另一个用户 Pod 的 25808 和 3092；
        - 各节点地址的 22、6443、10250 和抽样端口；
        - 本节点 cni0 网关地址；
        - 10.43.0.1:443、169.254.169.254:80、私网抽样地址；
        - 探针命名空间访问用户；
        - 一次性 Pod 的任何访问。
    - S11 预览来源校验：网关 Pod 带密钥访问 relay 返回 200；其他 Pod 带同样的密钥返回 403。
    - S12 nft 兜底（`--guard`）：只在测试命名空间里临时去掉 NetworkPolicy，用户 Pod 访问宿主仍然不通；6443 和 10250 是例外，报告里写明。
    - S13 网关重启：删除网关 Pod 后，用户 Pod 的 restartCount 不变，新网关能接管。
  - 清理：
    - 用 `trap` 保证总会执行，可以用 `e2e.sh --cleanup --prefix <p>` 重复执行；
    - 删除内容：两个命名空间（等它们消失）、StorageClass、带 `workpartner-e2e=<p>` 标签的 PV、脚本自己建的静态目录；`--guard` 加载的规则恢复到运行前的状态。
    - 结束时检查：没有残留带 `workpartner-e2e` 标签的对象。
