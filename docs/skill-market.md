# Skill market

The skills tab has official, company and personal sections. Official skills cannot be replaced or removed. Personal uploads are installed locally first. Sharing requires a display name, short description, example and confirmation of a test in a new conversation. A skill whose frontmatter sets `metadata.source-name` and an HTTPS `metadata.source-url` shows that source as a link on its card, opening in a new window. The preinstalled `share-skill` skill teaches both engines to extract a reusable method, replace concrete private details with placeholders, install it for the author, and submit only after the author confirms the test.

Set `market.approvers` to the identity provider's reviewer union IDs. An empty list disables submissions, while personal uploads remain available. Configure organization-specific `market.reservedPrefixes` and `market.protectedNames`; no organization account or name is embedded in the public default. Restart the gateway after changing these fields. The private deployment must resolve reviewer identities from its roster before enabling sharing.

`market.sharedDirectory` is the gateway's writable shared store, defaulting to `/shared-skills`. Mount `<runtime.hostData>/shared-skills` at that location in the gateway. Personal containers receive the same host directory at `market.containerDirectory` (default `/opt/shared-skills`) read-only. If you customize the gateway path, provide the matching host mount; the gateway uses `<runtime.hostData><market.sharedDirectory>` when creating personal containers. Pending submissions and review records remain under `<runtime.stateDirectory>/skill-market`, outside the shared mount. Use one gateway writer for this state directory and retain it in backups together with the shared directory.

Kubernetes uses `runtime.k8s.sharedSkillsClaim` (default `workpartner-shared-skills`). Before enabling `features.marketSkills`, provision a PVC with that name in each of the system and user namespaces. Both claims must expose the same shared filesystem, with write access for the gateway and read-only access for personal Pods. The renderer mounts the system claim at `market.sharedDirectory`; the runtime mounts the user claim at `market.containerDirectory`. The node-local storage class for personal workspaces does not supply this shared filesystem. The claims and their backing storage are operator-managed and are not created by the renderer. This keeps personal Pods compatible with the existing baseline admission policy. During Docker/Kubernetes migration, do not run two market writers against the same catalog or shared store; keep sharing disabled until a single writer owns it, or isolate their catalogs and libraries.

Each version needs approval. The application bot sends reviewers a card with approve and reject buttons that open the authenticated review page, matching the existing market's review-link approach. Reviewers can inspect every submitted file and confirm the decision there. Rejection requires a reason. The review page can resend cards, and the market's review history can resend failed result notices. Approval is saved before the live link is changed and before the author is notified. Notification failures remain visible and never undo a decision. A restarted gateway reconstructs live links from its saved decisions and restores missing approved releases from the private submissions. If a release cannot be restored, it logs and omits that skill while continuing startup; other skills remain available. Repeating approval or rejection for a processed version returns a conflict with its current status.

Submissions reject suspected credentials, phone numbers and identity numbers in files and market metadata. Internal addresses and local paths are highlighted for review. Cards state the number of scripts. Personal ZIP validation limits paths, file count and expanded size; shared exports are limited to 200 regular files and 10 MB in total. Review all files before approval: these checks do not establish that a skill is safe or useful.

Approved releases are immutable. Installing creates a link under both personal engine directories to a shared live link. The approved update switches that live link atomically; pending updates leave the previous release in use. Withdrawal removes it so new sessions stop discovering the skill. Installed links remain visible in Mine as withdrawn and can be removed with one click; removing them allows a personal upload with the same name. Already running conversations may retain instructions they loaded earlier. Installation counters keep only an aggregate of managed installed links, without an installer identity list. A successful uninstall decreases the count, so uninstalling and reinstalling does not inflate it. Manual changes to engine directories and a lost response can make the aggregate inaccurate; retrying an existing link never counts it twice.

`market.preinstalled` lists approved skills to install on workspace startup and protect from personal deletion. It defaults to empty. Adding a name replaces idle containers through the existing configuration update policy. Unavailable configured skills produce a startup warning. Skills installed normally remain optional and are never installed for everyone by default.

The container helper `wp-market` supports `list`, `submit`, `install`, `uninstall` and `withdraw`; it uses the signed personal identity prepared by the gateway. Submission uses the same JSON endpoint as the market page. Cookie mutations require the configured same origin; signed container mutations require a valid current roster identity. Authors retain their local draft while it is pending. Two authors cannot publish under the same name.

The helper reaches the gateway through `runtime.gatewayOrigin` from the organization configuration embedded in the user image. The gateway accepts that configured internal Host, so its hostname must resolve to the gateway on every personal container network; add a matching network alias if the gateway container has a different name. Build both the gateway and user image from the public export with matching organization configurations. A user image built directly with the private repository's build script retains the private market route namespace and cannot reach the public gateway's market endpoints.

Claude Code 2.1.319 and Codex 0.167.0 both followed the shared directory links during offline discovery, including an approved update and withdrawal. Re-run `python3 image/tests/verify-shared-engines.py --claude <binary> --codex <binary>` when changing engine versions. This check initializes the native discovery protocols and makes no model request. Start a new web conversation after installation; send `/new` in the personal messaging agent.

Deploy both gateway and user image, then verify with an author, reviewer and second installer in an isolated preview: share a sanitized method, approve through the bot card, install in the market, trigger it in both web engines and the personal messaging agent, approve a revision, withdraw it, and submit a fake credential. Offline checks and temporary-volume browser fixtures do not replace this deployment acceptance.
