# Organization configuration

`WORKPARTNER_ORG_DIR` selects the organization directory. The neutral configuration is in `org/default/organization.json`; its schema and the resolver in `gateway/organization/resolve.mjs` define the accepted fields. Copy the directory before customizing it. Store organization-specific values outside the source tree.

| Configuration group | Purpose |
| --- | --- |
| `displayName`, `productName` | Organization name and localized product names |
| `publicHost` | Your public HTTPS hostname and login callback host |
| `identity` | Provider, application identity, secret file reference and admission policy |
| `model` | Your model endpoint, key policy and agent defaults |
| `runtime` | Image, network, container names, limits and host data paths |
| `runtime.k8s.gatewayResources` | Optional gateway CPU and memory for the Kubernetes manifest renderer: `{"cpu":"500m","memory":"512Mi"}`. Each omitted field keeps that default. Values are positive Kubernetes resource quantity strings; requests and limits use the same values to retain Guaranteed QoS. |
| `appearance` | Neutral or custom assets and interface copy |
| `image` | Optional skills and instruction templates |
| `bridge` | Optional organization-owned messaging bridge template |

Set the public hostname and model endpoint explicitly. Give the login application its own credentials and reference secret files instead of placing secrets in JSON. The default configuration contains no organization accounts, admission group, private model endpoint, preinstalled organization skills or enabled messaging bridge. Branding assets and instructions belong to the selected organization directory.

`identity.callbackPath` selects the callback already registered with the login provider and defaults to `/_wp/callback`. The gateway handles both login and personal platform authorization on this path: states starting with `feishu-` use personal authorization, and all other states use the login callback, including onboarding and session issuance. The default `/_wp/callback` login route remains available when a different path is configured. State cookies cover both route namespaces.

The gateway reads `model.defaults` and the optional `model.catalog` from its mounted organization on each personal-container check. It passes the non-secret defaults and catalog in `WORKPARTNER_MODEL_CONFIG`. A changed configuration uses the existing idle-container replacement policy, even when the image name and image ID are unchanged. Active conversations delay replacement until idle under the same maximum deferral policy as image upgrades. No image rebuild or gateway restart is needed for subsequent model changes. A page request or the existing rollout tool triggers the check; refresh the page after the replacement.

For example, edit `model.defaults.claude` and `model.defaults.opus` in your mounted `organization.json`, then access an idle personal workspace. The replaced container receives the new Claude default and alias mapping. The other Claude aliases are `sonnet` and `haiku`; the neutral defaults are `claude-opus-5-5`, `claude-sonnet-5-5`, and `claude-haiku-5-5`. ChatGPT (Codex) defaults to `gpt-6.1-sol`. Engine model values follow changed organization defaults while they still equal the last organization value recorded in `.wp-organization-model.json` beside each engine configuration. Personal model changes, browser selections and conversation selections remain in effect. Markerless existing settings adopt the current default or the released initial default (`claude/claude-opus-5-5` for Claude and `gpt-6.1-sol` for Codex); other values are preserved.

At startup the resolver uses the injected configuration, falling back to the embedded organization only when none was supplied. Invalid injected configuration stops startup. First-run engine files use those runtime values. The seed publishes the runtime catalog and personal engine defaults through the existing `/api/settings/client` settings; the browser no longer embeds a model catalog in its build. A failed `/v1/models` permission lookup retains that runtime catalog.

Without `model.catalog`, the catalog has one configured default per engine. Optional entries are JSON arrays under `model.catalog.codex` and `model.catalog.claude`. An entry can reference a defaults field, such as `{ "default": "sonnet", "id": "sonnet" }`, or supply a literal `{ "id": "other-model", "key": "provider/other-model", "name": "Other model" }`. `also` lists native engine aliases for the same entry. Omit `name` on a default reference to display its configured model name. Put the intended default first. Catalog edits follow the same container replacement policy.

This code change requires one initial user-image rebuild and gateway deployment. Later model-default or catalog edits require only container replacement. Changes to branding, instructions or packaged software still require an image build.

Startup model discovery preserves the endpoint's route names and adds provider-qualified and bare names for catalog matching. This includes `provider/`, `group/`, `auto/` and `mp-*/` routes. The picker filters matching entries by those permissions and the engine's supported options, while keeping the current model visible. If permission matching removes every available catalog entry, it restores the engine-supported catalog instead of showing only the current model.

Set `bridge.template` to a template relative to the organization directory. The build renders model and effort placeholders and embeds the template; bot credentials remain outside the image. The image includes the bridge onboarding worker and authorization overlays; their HTTP endpoints are provided by the deployment gateway. Startup launches the bridge only when `/data/.cc-connect/config.toml` already exists. The pinned customized binary supports the template's preview and thread isolation options. The public downloader verifies its release digest; see [build input limits](deployment.md#current-preview-limits).

Optional `model.quickLineModel` selects a fast model for a temporary Feishu quick reply line (up to 30 characters) while a turn runs. It must be a string without carriage returns or newlines; omitted or empty disables auto-configuration. It travels in `WORKPARTNER_MODEL_CONFIG` and as `QUICK_LINE_MODEL` in both Docker and Kubernetes personal containers. Changes follow the same idle-container replacement policy as model defaults, including removal, without rebuilding the image after the initial upgrade. Startup preserves `QUICK_LINE_MODEL`; a personal-container environment override takes precedence (an empty override disables it). Auto-configuration also requires `ANTHROPIC_BASE_URL` and `PARTNER_MODEL_KEY_FILE`. Explicit `[stream_preview.quick_line]` bridge settings take precedence; no section is needed in the template. The line never enters the final reply. Enabling it makes additional requests to the selected model; leave it disabled until the organization approves that usage.

The personal messaging bridge uses Claude Code with `bypassPermissions` in the isolated workspace, `/data/work`, `model.defaults.claude` and `model.defaults.effort`. Onboarding and startup migrate existing bridge configurations using only the agent `type`, `mode`, `model`, `reasoning_effort` and `append_system_prompt` keys; bots, access lists, comments and other bytes are preserved. Repeated migrations do not write the file. A failure warns without stopping startup or onboarding. Optional `bridge.upgradeKeys` carries later template changes to existing configurations: each entry names a template key as a dotted table path (`queue_batch.debounce_ms`, `stream_preview.spinner_image`), `projects.platforms.options.<key>` for every platform of the template platform's type, or `projects.agent.options.<key>` for every project's agent, and an optional `from` list of superseded default values. Startup writes the rendered template's value when the key is missing or still holds a `from` value; any other personal value stays. The managed agent keys (`mode`, `model`, `reasoning_effort`, `append_system_prompt`) are rejected here. An organization-owned older template is migrated as well. Keep `agent_session_idle_timeout_mins` unset: closing the live agent prevents background completions from waking it. The managed `append_system_prompt` is the only place that tells the agent to acknowledge long work, end the turn and report when woken, because only the bridge resumes the session when background work completes. This does not change the web engine picker or personal web model choices.

To preview an existing config offline, run `python3 -I tools/migrate-bridge.py /path/to/config.toml --model your-claude-model --effort medium`; add `--apply` to write it. Run it as the workspace owner, or as an administrator who can preserve file ownership. Back up the configuration and stop the bridge before applying an offline migration so its own configuration writer cannot race the migration. Startup performs the same migration before launching the bridge. This tool does not modify saved conversations or convert historical Codex sessions into Claude sessions.

Child agents inherit `CLAUDE_CODE_SUBAGENT_MODEL`, defaulting to `model.defaults.haiku`; a container environment override is preserved. The shared background-task instructions are included even when `image.instructions` supplies older organization instructions. Web conversations and the bridge read the same instruction file, and web conversations are not resumed when a child agent finishes, so these instructions run child agents in parallel but wait for them within the same turn and give one final answer. Their memory placeholders use the effective cgroup limit (including per-person overrides), falling back to `runtime.nextMemory`. The policy allows up to two background tasks, each using at most a quarter of the workspace limit, capped at 512 MiB. These are agent instructions; the container memory limit enforces the total budget. After deployment, verify that a multi-minute web request with each engine ends with one final answer, and that the messaging app gives immediate acknowledgment, answers intervening messages and reports completion unprompted; source-level config checks cannot establish that live behavior.

`image.homeDirectory` supplies organization home templates, including an optional `feishu-SKILL.md` authorization policy. `image.instructions` supplies the company instruction block; `image.legacyInstructions` supplies exact historical templates. Startup replaces only the marked company block in personal instructions, preserving the surrounding bytes; pristine historical templates upgrade in full. Existing `AGENTS.md` files remain intact.

`image.skillTranslations` overrides entries from the generic `image/skills-zh.json`. `image.officialSkillsArchive` enables the official skill bundle. The public build supplies its reproducible archive from the two locked upstream source archives; direct materialization copies the configured local archive unless `WORKPARTNER_OFFICIAL_SKILLS_ARCHIVE` explicitly supplies a replacement. The installer retains references and licenses and groups the official skills under the generic `feishu` skill in the capability list. Organization-specific authorization instructions belong in the organization home policy.

`runtime.kind` selects the gateway's container runtime at startup: `"docker"` (the default) or `"k8s"`. Any other value stops gateway startup with an unsupported-runtime error. Docker preserves the current images, owner UID, mounts, resource limits, restart policy and per-user networks, including the `wpn-` bridge-name prefix used by host firewall rules. Container lifecycle, command execution, personal-volume file access and endpoint resolution go through this runtime.

The [Kubernetes operations guide](kubernetes.md) lists every Kubernetes and migration field, its consumer-side default, naming rules, deployment manifests, migration commands and recovery steps. `resolve.mjs` recursively merges organization JSON with the neutral defaults; it does not fill in `runtime.k8s` or `runtime.migration`, and there are no dedicated environment overrides for these fields. Docker-only organizations may omit them.

Kubernetes requires `runtime.k8s.namespace` for user workloads and `runtime.k8s.storageClass` for new data volumes. `runtime.k8s.systemNamespace` selects the namespace for system Pods and the image registry ConfigMap; it defaults to the client's namespace (the ServiceAccount namespace in-cluster, the selected context namespace with JSON kubeconfig). Set it explicitly for offline manifest rendering. Optional `runtime.k8s.systemContainer` names the container used by `execNamed(name)` in that system namespace. It must be a nonempty DNS label. When omitted, the container name equals the target Pod name (`name`); set this field if the names differ. Personal `exec(slug)` always targets the `workspace` container.

Optional `runtime.k8s.userImages` maps user slugs to image references (for example, `{"person":"workspace:pilot"}`) so individual users can try a new image first on Kubernetes. Each image must first be imported onto that user's node and registered in the `workpartner-images` ConfigMap. Removing an entry returns that user to `runtime.nextImage` when their workspace is idle; unlisted users keep the default image. Docker ignores this setting and logs a startup warning.

During migration, configure both gateways with `runtime.migration.ownersFile` pointing to the same shared file and `runtime.migration.peerOrigin` pointing to the other gateway's internal HTTP origin. Without `ownersFile`, each gateway considers all users its own. With ownership enabled, non-AionUi users always belong to Docker. Kubernetes skips organization extensions by default and checks owned, existing, zero-replica workspaces every `runtime.k8s.keepRunningIntervalMs` (default 300000 ms; 0 disables it). The presence of the StatefulSet annotation `workpartner/paused` skips that background check; it does not block user-triggered startup.

A stale workspace (image or environment changed) is replaced only when it is idle. Busy means an AionUi conversation is processing or the Feishu bridge has a turn in progress. The bridge check first looks for engine child processes under `cc-connect`; with none, the bridge is idle. If a child exists (Claude Code keeps an idle one for `idle_timeout_mins` after each turn), the gateway asks the bridge's local API socket (`/data/.cc-connect/data/run/api.sock`): it lists `/sessions` and reads `busy` from `/assistant/state` for each one. If any of those reads fails, the old rule applies and the child counts as busy. On Kubernetes, `runtime.k8s.reconcileImagesIntervalMs` (unset or 0 disables it) also replaces idle stale running workspaces in the background, so users who only use Feishu get the new image. It uses the same busy check and `maxJobs` limit, skips busy users until the next round, and never touches slugs in `runtime.k8s.reconcileExclude`.

The StatefulSet name (`runtime.nextContainerPrefix + slug`) must be a DNS label no longer than 52 characters, leaving room for the controller revision hash label and resource suffixes. Its Pod is named `<StatefulSet>-0`. Kubernetes `inspect` returns `replicas` from the StatefulSet specification and `annotations` from its metadata, defaulting to `null` and `{}` when absent. Its `address` is available only while the main container is running, has a Pod IP and is not terminating. These extra inspection fields do not change the Docker contract.

Workspace limits default to `runtime.nextMemory` (or 3221225472 bytes) and `runtime.nanoCpus / 1e9` (or 2 CPUs). The Kubernetes default CPU limit is 2 when `nanoCpus` is absent; Docker leaves it unlimited. Optional `runtime.k8s.userResources` overrides memory and/or CPU limits by slug when `create` builds or updates that person's workspace template. Values use Kubernetes resource quantities; unlisted users and omitted resources keep the global limits. Requests remain `runtime.k8s.memoryRequest` (default `512Mi`) and `runtime.k8s.cpuRequest` (default `100m`). For example, inside `runtime.k8s`, using a fictional slug:

```json
{
  "userResources": {
    "fixture-person": { "memory": "8Gi", "cpu": "2" }
  }
}
```

Repeated `create` preserves the current replica count and updates the template, clearing removed optional settings such as `runtime.k8s.userPriorityClass` and `runtime.k8s.newUserNodeSelector`. The StatefulSet uses `OnDelete`, so existing Pods need recreation to receive template changes. Model keys are mounted read-only from a Secret with `subPath`; updating the Secret also requires Pod recreation (for example, `restart`) before the new key becomes visible. One-off maintenance Pods retain the global limits and return at most 1 MiB of logs. `stop` and `remove` wait for all of the user's Pods to disappear; timeout errors name remaining Pods, and unrelated one-off Pods are not deleted automatically.

In Kubernetes mode every method on the legacy runtime throws `LegacyRuntimeUnavailable`. The following extension compatibility behavior applies to Docker deployments.

Organization-owned gateway extensions continue to receive the existing `docker(method, path, body, timeoutMs)` callback, returning `{status, body}` with a Buffer body. The synchronous `writeContainerToken(key, user, root='/users', uid=1001)` helper also remains available. New code can use the legacy personal runtime provided as `runtime` for `putFiles`, `readFile`, `removeFiles`, `exec`, `stop`, `remove`, and `address(slug, port, existing)` only. The legacy runtime does not expose other methods (including `inspect`, `create`, `runOnce`, and `ensureIsolation`); calling `address` without `existing` throws an unsupported-operation error. Use `personalRuntime` for the full next-container runtime. `writeContainerToken(key, user, runtime)` returns a Promise. Existing extensions can deploy without migration. Historical extension endpoints retain their supplied IP/address and port; an explicit `existing` value without an IP or address (including `null`) remains unavailable and does not trigger container discovery.

Configure reviewed sharing with `market.approvers`, `market.reservedPrefixes`, `market.sharedDirectory`, `market.containerDirectory` and `market.preinstalled`. See [skill market](skill-market.md) for mounts, review policy and acceptance. Empty approvers disable sharing.

## External data tools

Optional `dataTools.catalog` selects a JSON capability catalog inside the organization directory. Leave `dataTools` absent to expose an empty Tools tab and generate no data skill. The catalog uses `schemaVersion: 1`, localized `categories`, a `platforms` discovery map, `directory` paths and exclusions, and a `tools` array of common examples. Categories authorize access; examples supply direct commands and stricter request limits. See `tools/data-tools.test.mjs` for a complete neutral configuration and provider fixture.

The organization owns `dataTools.provider`: `origin`, existing `tokenFile`, `orgIdEnvironment`, `orgSlugEnvironment`, `enabledEnvironment`, `verifiedEnvironment`, `limitEnvironment` (`daily`, `monthly`, `call`), optional `overridesFile`, `budgetPath` and `usagePath` containing `{orgId}`, `callPath` containing `{id}`, and `headers` (`token`, `organization`, `tag`, `routeMax`, `cost`, `callId`). Enable and attribution-verification environment variables must both be `1` before spending. Credentials stay in gateway secret files. Defaults are USD 1/day, 5/month and 1/call; the override file maps person slugs to `dailyUsd`, `monthlyUsd` and `callMaxUsd`. Usage windows are UTC days/months.

Directory paths are `platformsPath`, `platformPath` and `endpointPath` (both with `{id}`), and `searchPath`. `blockedEndpoints`, `blockedProviders` and optional `blockedCapabilities` exclude generic web tools or other capabilities. Optional `mergedPlatforms` maps a small platform slug to another open platform of the same category: the small platform loses its own filter and its cards are listed, and labelled, under that platform. Access is unchanged. Localized `platformNames` and optional `presentation.tasks` / `presentation.endpoints` supply display copy. `presentationRedactions` removes provider labels from cards. Runtime metadata is cached for five minutes; failed reads are not cached. The gateway checks live platform categories, endpoint kinds, methods, paid eligibility and routed children. A common example never grants access to a closed category.

Authenticated routes are `GET /_wp/data/tools`, `GET /_wp/data/catalog?platform=ID`, `GET /_wp/data/search?q=QUERY`, `GET /_wp/data/info/ID`, `POST /_wp/data/call/ID` and `GET /_wp/data/usage`. Both gateway listeners apply the same identity and category policy before optional extensions. Optional `blockedPrefixes`, exact `legacyPassthrough` paths for legacy users, and `usageAliases` support organization-owned transitions.

The image includes `wp-data search`, `info`, `call` (with `key=value` or `--json`) and `balance`. Image preparation generates a `data-tools` skill with the category/platform map and direct examples. Existing startup exposes it to both agent engines and messaging sessions. The skill requires a unit-price quote before spending, actual cost and remaining allowance afterwards, and source citations. A call with an unknown outcome is never automatically retried. A usage-read failure after a completed call preserves the completed result.

### Content generation and file results

Add a localized category such as `{"en":"Content generation","zh":"内容生成"}` and its provider platforms to the same catalog. The provider's live platform category must match. Generation uses the existing data provider, personal identity and daily/monthly/per-call budgets; model gateway configuration does not change. Cards reuse the platform chip, price and fixed “Try it” prompt of other categories.

Common endpoint examples can set `defaults`, `timeoutMs` and `fileResult`, for example:

```json
{
  "defaults": { "model": "image-standard", "quality": "medium", "size": "1024x1024" },
  "timeoutMs": 180000,
  "fileResult": {
    "path": "data",
    "urlField": "url",
    "base64Field": "b64_json",
    "maxBytes": 8388608,
    "maxFiles": 4
  }
}
```

Every default key must appear in the endpoint's allowed `parameters`. Defaults fill omitted input; agents may override allowed parameters, while `rules.fixed` and other limits still apply. The generated skill's command and the card's “Try it” prompt combine `template` with these defaults. `wp-data info` exposes the execution policy for both endpoint IDs and command aliases. Organization defaults take precedence over template values in generated examples.

`timeoutMs` bounds the provider HTTP request, including the response body (1–600 seconds; default 60 seconds). The command reads this policy before calling and waits 20 seconds longer than the gateway. This supports slow image endpoints that hold the request open until generation completes. The provider must enforce budgets and charge only successful generations. The gateway passes through the successful cost and call ID; failed or timed-out requests are never retried automatically. A bare HTTP 202 acknowledgement is reported as pending, not as a completed image: job submission/polling APIs require a provider adapter that waits for completion. Do not resubmit an unknown or pending job.

`fileResult.path` selects an image array or object inside the provider JSON using dot-separated keys; use `""` for the root. Configure one or both of `urlField` / `base64Field` to match its image objects. Base64 is decoded inside the personal container. URL downloads send no gateway or provider credentials and reject redirects. Both paths enforce `maxBytes` per image (up to 32 MiB), `maxFiles` (up to 10), and PNG/JPEG/GIF/WebP signatures. The gateway also caps the entire JSON response at 64 MiB. Returned image URLs must be directly downloadable HTTP(S) resources.

The command saves files under `/data/work/outputs/images/<UTC-date>-<endpoint>-<unique-id>.<format>` and returns absolute `files` paths alongside `costUsd`, `callId` and personal usage. `WORKPARTNER_WORKSPACE` can select a different workspace for standalone use. Once saved, base64 payloads are omitted from command output. The generated skill tells every agent to show the saved images to the user. A local save failure returns a nonzero exit code with `fileError`, the successful generation cost and any files already saved; do not pay to regenerate. Workspace files are never uploaded automatically. Reference-image endpoints can accept existing public URLs as allowed parameters; local reference-image hosting is not implemented.

The Tools tab reads the live directory, displays personal remaining daily/monthly allowance, horizontal category buttons, platform filters and priced cards. Platforms follow the organization's `platforms` array; newly discovered platforms follow the configured ones. Common examples appear first within each platform and open a new conversation through “Try it”, with the generated `data-tools` skill already selected before the example text. The page never shows organization balances or provider names. An optional catalog `attribution` (`{"name": "…", "url": "https://…"}`) names the data source instead: the generated skill mentions it in its description, tells agents to cite it with the original source, and records it as the skill's source link. An optional catalog `skill` adds organization copy to the generated skill: `skill.description` (`zh`, `en`, one line each) is appended to the description that decides when agents load the skill, and `skill.guidance` (`zh`, `en`) opens the skill body with the organization's workflow. The complete description is limited to 1024 characters. Build a new personal image and gateway image when enabling these capabilities; organization catalogs and provider settings must also be mounted into the gateway.
Optional managed MCP hub configuration and tool display names are documented in [Managed MCP hub](mcp-hub.md).

`features.feedback` enables the feedback page at `/_wp/feedback` and the API at `/_wp/api/feedback`; it defaults to `false` and is read at startup. With it disabled, no feedback store is constructed and these paths retain the generic 404 response. The top-level `feedback` section defaults to `{"allow":[],"handlers":[],"botTokenFile":"/secure/feedback-bot.token","maxImageBytes":5242880,"maxImagesPerItem":6}`. `allow` accepts provisioned user slugs or union IDs (`"*"` allows every provisioned user); `handlers` contains union IDs and grants access to all feedback, even outside `allow`. Both lists are re-read through `organizationData()` on every user request without caching; read/parse failures make both lists empty. Other settings require a restart. Feedback state and private PNG/JPEG/WebP screenshots live under `${runtime.stateDirectory}/feedback/`; one gateway process owns the store. The submission limit is 30 per author per UTC calendar day.

User writes require same-origin cookies or a signed container `Bearer zpd.*` token. `/_wp/api/feedback/bot/` accepts only the service Bearer token from `botTokenFile`, re-read on each request, independent of the user allow list. Bots read `GET bot/changes?since=<seq>&limit=<n>` (default 50, maximum 200), item details and files, and write `POST bot/items/<id>` with status, bug-to-feature conversion, approval, an HTTPS PR link, or an idempotent `reply: {key,text}`. The changes feed contains the latest version of each changed item, including its author's union ID; user responses omit union IDs. Persist the returned `next` cursor after processing the batch. Status changes and new bot replies send a private Feishu message through the organization identity application; failed delivery does not undo the update, and `notice` records the result as a separate cursor-visible change.
