## 必改
1. **umask 泄漏给消息桥。** `wp-feishu-bot.py` 约 385 行在 main 里全局 `os.umask(0o077)`。supervise 也走 main，于是 cc-connect 和它拉起的 Claude Code 都继承了 077，从飞书那边新建的文件变成 600、目录变成 700，和网页那边（022）不一致。
   - 改法：不要全局改 umask。私密文件（缓存、状态、pid、FIFO）靠 mkstemp/mkfifo 0600 和 run 目录 0700 保护。cc-connect 子进程的 umask 必须和改动前一致（容器默认）。
   - 补测试：假 cc-connect 报告自己的 umask，断言等于守护进程启动时的原值（比如 022）。
2. **写状态文件失败会把消息桥永久停掉。** 约 267、315、327 行的 atomic_json，加上 350-380 行的主循环：写 bridge-state.json 或 bridge.pid 遇到 OSError（磁盘满、超配额、路径被占）时异常冒出，finally 里把 cc-connect 杀掉，守护进程以 1 退出，而且没人再拉起它。
   - 改法：写状态和 pid 失败只往 stderr 打一行警告，然后继续，不影响桥。主循环每一轮加兜底：意外异常记日志、退避后继续，守护进程不能因为非致命错误退出。
   - 补测试：把 bridge-state.json 换成目录（或让 run 目录不可写）。断言桥仍在运行，异常退出后仍会被重启，`restart` 仍然有效。

## 本轮一起做的建议
3. **DNS 超时。** 约 97-98 行，SIGALRM 挡不住卡住的 getaddrinfo。改法：请求前在一个守护线程里做解析，线程按剩余预算 join，超时就当作 feishu_unreachable。注释改成与实现一致。整个命令仍须在 8 秒内结束。
4. **stderr 被并进 stdout。** 约 320 行 `stderr=subprocess.STDOUT`。改成单独的管道：stdout 照原样转发到 sys.stdout，stderr 照原样转发到 sys.stderr，两路都过事件过滤（lark 日志可能走任一路）。
5. **cc-connect 路径。** 约 318 行按 PATH 找 `cc-connect`，用户的 `/data/.zp-init.d/bin` 在 PATH 最前面，同名文件会盖掉镜像里的。生产默认用绝对路径 `/opt/workpartner/bin/cc-connect`，测试用环境变量（比如 `WP_CC_CONNECT_BIN`）覆盖。
6. **事件匹配收紧到 lark SDK v3.12.2 的原文格式**，防止用户消息内容误触发。行内必须出现以下片段之一（来源 ws/client_session.go:70,90 和 client_lifecycle.go:199,213,215）：
   - `connected to wss://`（且不是 `disconnected to`）→ connected
   - `disconnected to wss://` → disconnected
   - `websocket reconnecting: attempt <数字>` → reconnecting
   - `websocket reconnect attempts exhausted after <数字> attempts` → exhausted
   - 补测试：只含单词 reconnecting 或 connected 的普通行不改状态。
7. **删掉 `image/tests/feishu-bot-offline.test.py`**，它只是为了绕开沙箱。确认它覆盖的断言在真实 HTTP 测试 `feishu-bot.test.py` 里都有，缺的补到真实 HTTP 测试里（沙箱里跑不了没关系，协调者本机跑）。
