## A. Linux tests (CI: 1 failing of 701)

A1. `tools/gateway.test.mjs` — "my key preview on and off preserve original serializer bytes unless admitted" fails on
`assert.ok(!fs.existsSync('<state>/my-key'))`. Loading the gateway and serving `/_wp/preview/client.js` now creates `S/my-key`
(the reset module creates its directories when it is constructed / when it starts recovery). That invariant is deliberate and must
hold again: **constructing the handler, start-up recovery, a GET, a status poll, a heartbeat check and serving the client script must
never create `S/my-key` or anything below it.** Recovery only reads what exists. Directories are created lazily, at the moment a
reset request is actually accepted (the POST that is about to write `active/` and `requests/`), and by audit writes exactly as
before this change. Do not weaken the existing test. Add a test in `gateway/tests/my-key-reset.test.mjs` that constructs the handler
with reset enabled, runs GET `/_wp/api/my-key` and GET `/_wp/api/my-key/reset` for an admitted person with no `S/my-key` present and
asserts nothing was created and that the reply is the "unavailable" state (no heartbeat).

## B. Browser tests (CI: 4 failing of 29 in group `my-key`)

B1. Root cause of three failures ("…masked success with a real gateway", "pending polling stops on close…", "POST conflicts, quota
and policy changes…"): the fixture container API in `tools/browser-tests/lib/harness.mjs` answered `POST /containers/<name>/restart`
with 200 and a JSON body; the Docker runtime expects 204, so the gateway's install step failed at `restart` and retried forever
(audit: `retry … step restart`) and the dialog never reached "done". The uncommitted edit adds a 204 reply and records the container
name in a `restarts` array. Finish it: expose it on the object returned by `startGateway` (for example `gateway.restarts`), and in
the success test assert that exactly one restart was requested and that it was for the signed-in member's container; in the
failure/offline/blocked tests assert that none was.

B2. Root cause of the fourth ("blocked notes, daily limit, unavailable and feature off…", state `limit`): `route.fetch()` resolves the
fixture host from the test process, which cannot reach it (`getaddrinfo ENOTFOUND`), so the dialog stayed on "loading" and an
unhandled rejection was reported after the test. The uncommitted edit asks the gateway directly through `gateway.request('GET', API,
{ who: 'member' })` and fulfils the route with that JSON. Check that no other test in the file uses `route.fetch()` against the
fixture host; make sure routes are removed (`page.unroute`) before the page closes so no handler runs after the test has ended.

B3. With B1/B2 applied all eight `reset:` browser tests passed on a machine that can run Chrome. Keep the file-only stand-in broker in

## C. The two halves have never run against each other — add one integration test (no sockets, no browser)

Each half is tested against its own fixture of the other. Add `tools/key-reset-integration.test.mjs` (picked up by
`node --test tools/*.test.mjs`) that wires the **real** gateway handler (`createMyKey…` exactly as `gateway/tests/my-key-reset.test.mjs`
builds it, calling `handle(req, res)` directly — no listening socket) to the **real** broker (`createBroker` with the real Python
helpers through the real bootstrap, executed locally, as `tools/key-reset-broker.test.mjs` does) over one temporary directory tree,
with a JSON key-store file and a small rotate program that reads the new value from stdin. Skip cleanly if `python3` is missing. Cases:

1. Success end to end: heartbeat appears → GET shows reset allowed → POST 202 → broker loop claims, stages, rotates, writes the
   result → gateway installs (same inode), calls `rekey`, `inspect`, `restart` once → status `done`, `left` 2. The key file now holds a
   value with the configured prefix that is the only value the store entry accepts; every other field of the store entry is unchanged;
   both audits have their line for this id; neither audit, no file under `R`, no broker-local state file and no reply body contains
   the old or the new value.
2. Policy seen by both sides: person in `reset.blocked` → gateway 403 and, if a request file is forged for that person anyway, the
   broker answers `denied` and the key is unchanged.
3. Broker not running (no heartbeat) → gateway 503 `unavailable`, nothing written, key unchanged.
4. Rotate program fails → result `rotate-failed`, gateway reports failure, key file and store unchanged, `.next` gone, the person can
   try again.
5. Gateway handler replaced (simulated restart) after the broker wrote the `ok` result but before the gateway processed it → the new
   handler finishes the installation.
6. Broker replaced (simulated restart) after rotation but before the result was delivered → the new broker resolves by hash, delivers
   `ok`, the gateway installs.
7. Daily limit across both: three successes, the fourth is refused by the gateway; a forged fourth request file is refused by the
   broker with `limit`.

Any mismatch you find between the two halves while writing this test is a bug to fix in the code, not in the test; list each one in
the report.
