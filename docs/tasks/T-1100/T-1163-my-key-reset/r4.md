## F1. `tools/key-reset/key-store.py` — only a rotate process that really ran and exited with an ordinary failure is `rotate-failed`

Today any non-zero `returncode` with the old hash still stored returns `rotate-failed`, and the helper on the gateway host then deletes
the staged `.next` file. But a non-zero status does not always mean the rotation will not happen later:
- a negative `returncode` means the local client (the container exec client or whatever the configured command is) was killed by a
  signal — for example by the out-of-memory killer on a busy host — while the process it started inside the container may still be
  running and may still write the new value;
- `125` and above are the conventional "the exec client itself failed / could not invoke / was interrupted" statuses, which say
  nothing about whether the in-container process ran.

Change the rule to: return `rotate-failed` only when `completed` is not `None`, `1 <= completed.returncode <= 124`, and the entry
still holds the old hash. Everything else that does not show the new value (negative status, `>= 125`, timeout, OS error, `0` without
a change) returns `unknown`, which the broker already handles with the ten-minute quiet period and three separate checks.

Update `docs/key-reset.md` where it describes when the store helper answers `rotate-failed` versus `unknown`.

Tests: extend the existing "store helper returns unknown on timeout, OS error or zero exit without a change…" broker test (or add one
next to it) with a rotate command that kills itself with a signal and one that exits `125` while the store keeps the old hash —
both must return `unknown` — and keep one that exits `1` with the old hash returning `rotate-failed`.
