## F1. `tools/key-reset-broker.mjs` `start()` — stale lock detection under a hardened service

The broker is meant to run as a service with no capabilities and with other users' `/proc/<pid>` entries hidden. After a reboot the
PID recorded in `broker.lock/` may belong to a process of another user. Then `process.kill(pid, 0)` fails with `EPERM` (treated as
alive today) and `processStart(pid)` returns `null` (treated as "cannot tell, assume alive"), so the broker refuses to start forever
with `broker-running`.

The lock owner is always a broker process running as the same user as the current one, so:
- treat the recorded owner as alive **only** when `process.kill(pid, 0)` succeeds; any error (`ESRCH`, `EPERM`, anything else) means
  stale;
- when the signal succeeds, keep today's start-time comparison (`!started || 'unknown' || equal` → alive).

Do not change the gateway's per-person `lock()` in `gateway/my-key-reset.mjs`.

Test in `tools/key-reset-broker.test.mjs`: a lock whose owner name carries a PID for which the signal check fails with `EPERM` is
treated as stale and the broker starts. Make the check injectable if needed (for example an optional `signal` / `processStart`
dependency, defaulting to the real ones), the way other broker tests inject the clock. Keep the existing lock tests passing.

Update the lock paragraph in `docs/key-reset.md` with one sentence on this rule.
