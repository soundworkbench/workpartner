M3. **An uncertain rotation must never be treated as a failed one** (security, medium). Today: `tools/key-reset/key-store.py`
swallows `subprocess.TimeoutExpired` from the rotate command and then, because the store still shows the old hash, returns
`rotate-failed`; the broker likewise turns a transport failure into an immediate `which` check and, seeing the old hash, decides
`rotate-failed`; the gateway-host helper then deletes the `.next` file on `ok:false`. But killing the local client (docker CLI or
ssh) does not stop a rotation already running on the far side, which may still write the new value later — the person would then
have no usable key. Required behaviour:
- `key-store.py`: a timeout, an OS error, or a non-zero exit **combined with the stored hash not yet showing the new key** returns
  `unknown` unless it can positively prove the rotation did not and will not happen. Return `rotate-failed` only when the rotate
  command itself exited (no timeout) with a failure status *and* the entry still holds the old hash. Never `rotate-failed` after a
  timeout. Reject an entry identifier that starts with `-` (code `rotate-failed` before anything runs is fine, since nothing ran).
- Broker: an `unknown` outcome at the rotate step keeps the attempt **unresolved** — the slug stays busy, the `.next` file stays,
  the plaintext stays only in memory as today. Each cycle it re-checks the store: new hash present → continue forward exactly like a
  successful rotation (deliver `ok:true`); old hash still present → keep waiting. Only after **at least 10 minutes since the
  rotation started and three consecutive checks (in different cycles) that still show the old hash** may it decide `rotate-failed`
  and deliver `ok:false`. A broker restart in the middle must resume this from its inflight record (it already resolves by hash —
  keep that; the plaintext is not needed because the staged `.next` file holds it on the gateway host). Audit lines record the
  waiting (code `rotate-unknown`, no key material), once per state change, not every cycle.
- Gateway side: while the result is pending the person keeps seeing the pending state; the existing 5-minute client polling cap is
  fine (the dialog then just stops polling; reopening resumes).
- Tests: in `tools/key-reset-broker.test.mjs` a rotate that times out but lands later continues to `ok:true`; a rotate that times
  out and never lands ends in `rotate-failed` only after the quiet period and three checks (use the injectable clock); `.next` is
  kept throughout; restart mid-way resumes. In `key-store.py` tests (or through the broker tests) a timeout returns `unknown`.

## S. Should fix (do them all; each is small)

S1. `gateway/my-key-client.mjs` — when the reset POST fails at the network level (no HTTP reply), do not immediately say the key is
unchanged: first `GET /_wp/api/my-key`; if `reset.status === 'pending'` switch to the normal pending/polling path; only otherwise
show the failed message. Browser test for this (abort the POST after letting the server accept it).

S2. `gateway/my-key.mjs` — the main `GET /_wp/api/my-key` must not fail because the reset summary cannot be read (corrupt day file,
`EACCES` on the reset directory): catch it and report `reset.reason: 'unavailable'` (with `allowed:false`), still serving the masked
key, usage and guide. Unit test.

S3. `tools/key-reset-broker.mjs` around the inflight scan (~line 404): read each inflight file in its own try; a malformed one is
skipped for that cycle and audited once as `stuck` (no key material), it must not crash the cycle or the process. Unit test.

S4. Broker single-instance lock: do not rely on `kill(pid, 0)` with a PID file in the persistent state directory. Use an advisory
lock that the kernel releases on exit (e.g. hold an open file descriptor with an exclusive `flock`-style lock — if Node lacks flock
use a lock *directory* plus a start-time check, the same way the gateway lock compares process start times) and treat
`pid === process.pid` as stale. Document where the lock lives. Unit test for a stale lock left by a dead process whose PID is reused.

S5. Broker: after a successful rotation, **deliver first, then record the local `done` count**; a failure to write the local count
must not block delivery (retry the count on the next cycle; it must still be counted before the slug can start another attempt the
same day). Unit test.

S6. Broker: write the `seen/<id>` replay marker only after the claim succeeded (or remove it when the claim transport failed without
the remote rename happening), so a transport failure does not turn a valid request into `replay`. Keep replay protection for real
duplicates. Unit test.

S7. `tools/key-reset/gateway-host.py` `Paths.path` for kind `next`: find the staged file by **exact name**
`P + slug + ".key." + id + ".next"` where `P` is the key prefix from the organization file; if the organization file is unreadable,
fail (`no-key` or the existing failure code) rather than suffix-matching. Unit/integration test with two slugs where one is a suffix
of the other (`bob` and `a-bob`).

S8. `gateway/my-key-reset.mjs` `lock()`: an unrecognised entry in the lock directory must not block a person forever. Entries older
than the claim timeout (or 10 minutes, whichever is larger) that do not match the expected pattern are removed, with one audit line
(`lock-cleared`, no key material); younger ones keep today's busy behaviour. Unit test.

S9. `gateway/my-key-reset.mjs` key installation: open the key file and read the staged file with `O_NOFOLLOW`; add a short comment
explaining why the in-place rewrite (same inode, for read-only bind mounts) is acceptable (the container is restarted right after).

S10. Heartbeat freshness: also reject heartbeats whose time is more than 30 seconds in the future. Unit test.

S11. Retention: the gateway prunes `R/days/<slug>-<date>.json` older than 7 days and `done()` only looks at today's file; the broker
prunes its own day files older than 7 days. Unit test for each.

S12. `docs/key-reset.md`: state that the broker reads the key prefix from the organization file's `model.keyPrefix` only, so a
deployment that overrides the prefix through the environment is not supported by the broker (it will answer `no-key`, safely). Also
document the new `rotate-unknown` code, the quiet-period rule from M3, the lock location from S4 and the retention from S11.
